# 线索配置设计文档

本文档定义场景线索如何放入房间、如何由玩家交互、以及如何与流程系统解耦。按全新项目标准设计，不考虑旧数据兼容。

---

## 1. 核心方案

线索系统拆成四层：

| 层级 | 负责内容 | 不负责内容 |
|---|---|---|
| `ClueData` | 线索文本、分类、父子线索关系 | 线索出现在哪个场景 |
| `CluePlacementData` | 某条线索在哪个房间、哪个挂点、什么流程条件下出现 | 线索文本 |
| `CluePlacementManager` | 房间加载后按当前流程动态生成线索交互点 | 线索 UI、线索状态 |
| `ClueItem` | 玩家按交互键后发现线索并打开详情 | 决定自己是否出现 |

基本原则：

- 场景只放挂点，不直接写线索内容。
- 线索内容只写在 `ClueData.tres`。
- 线索摆放只写在 `CluePlacementData.tres`。
- 玩家是否已获得线索只由 `DataManager` 判断。
- 当前流程节点只由 `FlowManager` 提供。
- `CluePlacementManager` 只做“当前房间应该生成哪些线索交互点”。

```text

```

说明：

- `assets/objects/clue_placements/` 存线索摆放定义。
- `scenes/objects/clue_item.tscn` 是通用交互点场景，所有场景线索复用它。

## 3. ClueData

`ClueData` 是纯内容资源。

```gdscript
class_name ClueData
extends Resource

@export var id: String = ""
@export var title: String = ""
@export_multiline var description: String = ""

@export var chapter_id: String = ""
@export var room_id: String = ""

@export var category_path: PackedStringArray = PackedStringArray()
@export var tags: PackedStringArray = PackedStringArray()

@export_enum("scene_evidence", "testimony", "conclusion", "lore")
var clue_type: String = "scene_evidence"

@export var is_conclusion: bool = false
@export var highlight_visible: bool = true

@export var parent_clue_id: String = ""
@export var child_clue_ids: PackedStringArray = PackedStringArray()
```

约定：

- `id` 必须全局唯一，文件名与 `id` 一致。
- `room_id` 是线索内容归属，不等于实际摆放位置。实际摆放位置由 `CluePlacementData` 决定。
- 口供线索也使用 `ClueData`，但不生成 `ClueItem`，由对话或流程调用 `DataManager.add_clue()`。
- 深入调查只配置父子关系，不额外摆子线索交互点。

## 4. CluePlacementData

`CluePlacementData` 是线索摆放资源，描述“某个流程下，某个房间的某个挂点应该生成哪条线索”。

```gdscript
class_name CluePlacementData
extends Resource

@export var placement_id: String = ""
@export var clue_id: String = ""

@export var chapter_id: String = ""
@export var room_id: String = ""
@export var spawn_name: String = ""

@export var available_steps: PackedStringArray = PackedStringArray()
@export var required_flags: PackedStringArray = PackedStringArray()
@export var blocked_flags: PackedStringArray = PackedStringArray()

@export var hide_after_discovered: bool = false
@export var interact_id: String = ""
@export var source_id: String = ""

@export var scene_path: String = "res://scenes/objects/clue_item.tscn"
```

字段说明：

- `placement_id`：摆放点唯一 ID，用于调试和存档，不等于 `clue_id`。
- `clue_id`：对应 `ClueData.id`。
- `room_id`：房间 ID，必须和房间脚本 `room_id` 对齐。
- `spawn_name`：房间内 `ClueSpawnPoints/{spawn_name}`。
- `available_steps`：为空表示该章节任意流程节点都可出现；不为空则必须匹配 `FlowManager.current_step_id`。
- `required_flags`：所有 flag 为 true 才出现。
- `blocked_flags`：任一 flag 为 true 就不出现。
- `hide_after_discovered`：发现后是否从场景消失。调查类线索通常为 `false`，拾取类线索才设为 `true`。
- `interact_id`：传给 `ClueItem.interact_id`，为空时使用 `placement_id`。
- `source_id`：传给 `DataManager.add_clue()` 的来源，便于后续统计；为空时使用 `placement_id`。
- `scene_path`：允许特殊线索使用自定义场景，默认使用通用 `ClueItem`。

第一章直接按正式结构落地：一条场景线索对应一个 `CluePlacementData.tres`。资源数量变多后可以增加编辑器辅助工具批量创建资源，但不引入脚本内配置表。

## 5. 房间场景约定

所有需要放场景线索的房间统一增加：

```text
Room
├── ClueSpawnPoints
│   ├── Desk
│   ├── Bed
│   ├── Window
│   └── Bookshelf
└── DynamicClues
```

约定：

- `ClueSpawnPoints` 只放 `Marker2D`，不挂脚本。
- `DynamicClues` 由 `CluePlacementManager` 清空和挂载 `ClueItem`。
- 手工摆放的装饰物、TileMap、Sprite 不负责线索逻辑。
- 线索交互范围、提示图标、碰撞形状都由 `clue_item.tscn` 或自定义线索场景提供。

房间脚本建议提供：

```gdscript
func get_dynamic_clues_root() -> Node2D:
    return find_child("DynamicClues", true, false) as Node2D


func get_clue_spawn_point(spawn_point_name: String) -> Marker2D:
    var root: Node = find_child("ClueSpawnPoints", true, false)
    if root == null:
        return null
    return root.find_child(spawn_point_name, true, false) as Marker2D
```

## 6. CluePlacementManager

`CluePlacementManager` 建议注册为 Autoload：

```text
CluePlacementManager="*res://scripts/clues/clue_placement_manager.gd"
```

职责：

- 启动时扫描并注册所有 `CluePlacementData`。
- 监听 `EventBus.room_loaded(room, room_id)`。
- 根据 `room_id`、`FlowManager.current_step_id`、`DataManager.world_flags` 和 `DataManager.has_clue()` 筛选摆放。
- 清空当前房间 `DynamicClues`。
- 实例化 `ClueItem`，设置 `clue_id`、`clue_def`、`interact_id`、`source_id`。
- 把实例放到 `ClueSpawnPoints/{spawn_name}`。

不负责：

- 不直接修改流程节点。
- 不打开 UI。
- 不维护线索发现状态。
- 不处理对话线索。

---

## 7. 运行流程

```text
SceneManager 加载房间
-> EventBus.room_loaded(room, room_id)
-> FlowManager 生成 NPC
-> CluePlacementManager 清空 DynamicClues
-> CluePlacementManager 筛选当前 room_id + step_id 可用的 placements
-> 实例化 ClueItem
-> 玩家靠近 ClueItem
-> PlayerInteractionArea 选择最近 Interactable
-> 玩家按 F
-> ClueItem.interact()
-> DataManager.add_clue(clue_id, "scene", source_id)
-> EventBus.clue_interaction_details_requested(payload)
-> ClueUI 打开交互详情
```

`FlowManager` 和 `CluePlacementManager` 都监听 `room_loaded` 没问题。两者不应互相直接调用。线索生成不依赖 NPC 生成结果。

## 8. 筛选规则

建议按以下顺序判断：

```gdscript
func _is_placement_available(placement: CluePlacementData, room_id: String) -> bool:
    if placement.room_id != room_id:
        return false

    if not placement.available_steps.is_empty():
        if not placement.available_steps.has(FlowManager.current_step_id):
            return false

    for flag_id: String in placement.required_flags:
        if not DataManager.get_world_flag(flag_id):
            return false

    for flag_id: String in placement.blocked_flags:
        if DataManager.get_world_flag(flag_id):
            return false

    if placement.hide_after_discovered and DataManager.has_clue(placement.clue_id):
        return false

    return true
```

不要把复杂剧情判断写在 `ClueItem` 里。`ClueItem` 只负责交互后发现线索。

## 9. ClueItem

`ClueItem` 是场景中的可交互实例。

必须字段：

```gdscript
@export var clue_id: String = ""
@export var clue_def: ClueData
@export var source_id: String = ""
```

交互行为：

- 第一次调查：加入父线索，打开父线索详情。
- 如果父线索有子线索，第二次及以后调查：解锁子线索，打开父子分层详情。
- 普通线索可重复调查，每次打开该线索详情。
- 是否调查后消失由 `CluePlacementData.hide_after_discovered` 决定，不由 `ClueItem` 自己决定。

深入调查规则保留在 `DataManager`：

```text
ClueItem
-> DataManager.add_clue(parent)
-> DataManager.get_child_clue_ids(parent)
-> DataManager.mark_deep_unlocked(parent)
```

## 10. 正式配置方式

所有场景线索摆放都使用 `CluePlacementData.tres`，不使用代码表。`CluePlacementManager` 启动时扫描 `assets/objects/clue_placements/`，把所有 placement 注册到内存中。

示例资源：

```text
assets/objects/clue_placements/ch1_snow_villa/ch1_wu_room_body.tres
```

示例内容：

```gdscript
[resource]
placement_id = "ch1_wu_room_body"
clue_id = "1_wu_1"
chapter_id = "1"
room_id = "room_wu_ting_xiang"
spawn_name = "Body"
available_steps = PackedStringArray("ch1_2_first_search")
required_flags = PackedStringArray()
blocked_flags = PackedStringArray()
hide_after_discovered = false
interact_id = "ch1_wu_room_body"
source_id = "ch1_wu_room_body"
scene_path = "res://scenes/objects/clue_item.tscn"
```

命名规则：

- 文件名与 `placement_id` 一致。
- `placement_id` 格式推荐：`{chapter}_{room}_{point}`，例如 `ch1_wu_room_body`。
- 同一条 `clue_id` 可以有多个 placement，但必须有明确理由，例如不同时期同一线索出现在不同房间。
- 同一个 `room_id + spawn_name + available_steps` 不应配置多条 placement，避免交互点重叠。

扫描规则：

```text
CluePlacementManager
-> 扫描 assets/objects/clue_placements/
-> 只注册 CluePlacementData
-> 按 room_id 建索引
-> room_loaded 时只检查当前房间的 placements
```

这样可以保持运行时高效：不会每次房间加载都遍历全部线索定义，也不会把线索摆放写死在脚本里。

## 11. 第一章落地策略

优先落地当前流程会进入的房间：

1. `floor2`：通常不放正式线索，只作为管家引导过场。
2. `room_wu_ting_xiang`：第一轮搜证重点房间，先放案发现场相关线索。
3. `hall`：大厅可放公共环境线索，但要小心不要和自由交互 NPC 抢交互点。
4. `shu_fang`：第二轮搜证房间，放研究所/书房相关线索。

建议先只做 `room_wu_ting_xiang`：

```text
room_wu_ting_xiang.tscn
├── ClueSpawnPoints
│   ├── Body
│   ├── Window
│   ├── Desk
│   └── Floor
└── DynamicClues
```

对应 placements：

```gdscript
[
    {
        "placement_id": "ch1_wu_room_body",
        "clue_id": "1_wu_1",
        "room_id": "room_wu_ting_xiang",
        "spawn": "Body",
        "available_steps": ["ch1_2_first_search"],
    },
]
```

具体 `clue_id` 以 `assets/objects/clues/ch1_snow_villa/` 中实际资源为准。

## 12. 与 Dialogic 的关系

Dialogic 不直接控制场景线索生成。

允许 Dialogic 做两件事：

- 对话中获得口供线索：调用 `DataManager.add_clue("1_testimony_xxx", "dialogue", timeline_name)`。
- 对话中改变流程条件：设置 Dialogic 变量或发出 `flow:*`，由 `FlowManager` 或 `DataManager.world_flags` 影响线索摆放。

不建议 Dialogic 做：

- 实例化 `ClueItem`。
- 直接隐藏或显示场景线索节点。
- 直接查找房间节点。

---

## 13. 存档边界

后续存档需要保存：

- `DataManager.clue_states`
- `DataManager.world_flags`
- `FlowManager.current_chapter_id`
- `FlowManager.current_step_id`
- 必要时保存当前房间

不需要保存：

- 已实例化的 `ClueItem` 节点。
- `DynamicClues` 子节点。
- `ClueSpawnPoints`。

读档后重新加载房间，`CluePlacementManager` 会根据保存状态重新生成当前可见线索。

## 14. 验收标准

最小闭环：

```text
进入 room_wu_ting_xiang
-> CluePlacementManager 读取当前 step = ch1_2_first_search
-> 清空 DynamicClues
-> 在 ClueSpawnPoints/Desk 生成 ClueItem
-> 玩家靠近后出现 F 提示
-> 按 F
-> DataManager.add_clue(clue_id)
-> ClueUI 打开该线索详情
-> 再次进入房间不会重复创建状态，只会重新生成交互点
```

深入调查闭环：

```text
父线索第一次调查
-> 只显示父线索
父线索第二次调查
-> DataManager.mark_deep_unlocked(parent)
-> 子线索进入线索手册
-> ClueUI 显示父子分层详情
```

条件生成闭环：

```text
required_flags 未满足
-> 不生成线索
流程或对话设置 flag
-> 重新进入房间
-> 生成线索
```

## 15. 实施顺序

1. 新建 `CluePlacementData`。
2. 新建 `CluePlacementManager` Autoload。
3. 新建通用 `scenes/objects/clue_item.tscn`。
4. 给 `room.gd` 增加 `get_dynamic_clues_root()` 和 `get_clue_spawn_point()`。
5. 给目标房间增加 `ClueSpawnPoints` 和 `DynamicClues`。
6. 先为 `room_wu_ting_xiang` 配 1 到 3 条线索。
7. 验证基础交互、重复调查、深入调查。
8. 再批量补第一章其它房间。

## 16. 以后再扩展

以下情况出现后再增强：

- 一个房间同一流程下线索数量很多：用编辑器工具或表格导入批量生成单条 `CluePlacementData.tres`。
- 某些线索需要特殊动画或小游戏：让 `CluePlacementData.scene_path` 指向自定义线索场景。
- 某些线索需要多阶段变化：增加 `variant_id` 或用多个 placement + flags 控制。
- 需要编辑器辅助批量摆放：写 EditorPlugin 或导入表格生成 `CluePlacementData`。

当前阶段不要过度设计。先把“配置生成线索 -> 交互获得线索 -> UI 展示详情”跑通。
